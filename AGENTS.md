### Global Sol Coordinator and Luna Delegation Policy
* Keep the main thread on the user-selected model and reasoning level. Treat it as the coordinator responsible for requirements, planning, final architecture and cross-cutting design decisions, ambiguous decisions, integration, and final verification.
* Before delegating a substantial, clearly bounded production package, classify it as HIGH or XHIGH using the routing policy below, then assign explicit ownership before Sol starts workspace execution. Use `luna_worker` for HIGH and `luna_worker_xhigh` for XHIGH. Luna owns the complete scoped loop: required project-document reading, relevant file discovery and reading, repository searches, implementation and edits, MCP and other tool calls, compilation or refresh, Console and log inspection, focused tests, scoped debugging and repair iterations, and final self-validation.
* Once Sol delegates a package, Sol must not perform that package's project-file reads, repository searches, edits, MCP calls, compilation, Console or log inspection, tests, or routine validation. Sol may read mandatory agent or skill instructions, make coordinator-level decisions, review Luna's compact handoff, and inspect a small critical diff only when an integration risk requires it.
* Give Luna a compact, self-contained task capsule containing the intended outcome, owned files or edit surface, relevant source paths, constraints and protected areas, acceptance criteria, required validation, and handoff format. Use `fork_turns="none"` or the minimum conversation history when supported; Luna may inspect adjacent dependencies to diagnose a blocker but must not expand its edit scope without Sol approval.
* Keep large raw MCP responses, logs, searches, and broad source context in Luna's thread when Luna can digest them. Luna's handoff should be concise and evidence-based: status, files changed, behavior implemented, commands or tools used, actual validation results, remaining risks or blockers, and the next action if any.
* Reuse one Luna worker for a coherent package and its in-scope repair iterations. A HIGH worker should handle ordinary in-scope implementation and validation repairs itself. Start an XHIGH worker for the same package only when the escalation criteria below are met; after escalation, XHIGH owns the remaining package. Spawn additional workers only for genuinely independent, non-overlapping packages; do not fragment work into microscopic subtasks.
* Sol should review critical diffs and integration boundaries and decide whether Luna's evidence is sufficient. Sol must not repeat Luna's searches, MCP checks, tests, or validation. If a later change, conflicting evidence, or integration risk invalidates a check, route the new check back to the same Luna worker first.
* Do not delegate trivial one-step work where coordination would cost more than doing it directly. Do not delegate final architectural choices, cross-cutting product decisions, destructive actions, credential/permission decisions, or final sign-off.
* Luna, especially XHIGH, may investigate architectural implications, trace cross-system behavior, determine root causes, and compare implementation approaches within an architectural direction already selected or bounded by Sol. If Luna discovers a genuinely unresolved architectural choice, authority ambiguity, conflicting requirements, or a decision that would materially change system boundaries, public contracts, or product behavior, it must return evidence and options to Sol instead of choosing. Sol makes the decision and sends Luna a revised bounded package for execution.
* If Luna stops because of a transient capacity, overload, interruption, or tool-service error, resume the same Luna worker with a concise delta-only continuation and let it inspect the existing workspace state instead of starting over. Retry the same worker up to two times when the failure is plausibly transient.
* If the selected Luna worker remains unavailable after those retries, report the delegated package as incomplete. If HIGH reaches a genuine reasoning blocker or returns insufficient or conflicting evidence, apply the HIGH-to-XHIGH escalation policy below. If XHIGH remains blocked or returns insufficient or conflicting evidence, stop and report the delegated package as incomplete. Do not shift substantial execution to Sol or an unrelated model unless the user explicitly authorizes that fallback. Work that proves too cross-cutting or ambiguous returns to Sol for a scope or architecture decision, then goes back to the appropriate Luna worker as a revised bounded package.
* For parallel edits, assign non-overlapping files or responsibilities. Sol owns conflict resolution, integration review, and final sign-off.

#### Luna Reasoning-Effort Routing
* HIGH is the default. When uncertain between HIGH and XHIGH, choose HIGH.
* Use `luna_worker` (GPT-5.6 Luna HIGH) when requirements are clear; implementation is localized or moderately scoped; an existing project pattern can be followed; debugging, Unity work, Unity MCP interaction, compilation, Console fixes, refactoring, tests, or validation are routine; the root cause is reasonably constrained; architectural ambiguity is low; regression risk is ordinary; and the work can be bounded cleanly.
* Use `luna_worker_xhigh` (GPT-5.6 Luna XHIGH) from the start only when one or more of these materially apply: the root cause is genuinely unknown; investigation crosses several interacting systems; networking, synchronization, concurrency, race conditions, authority, replication, or lifecycle behavior is central; deep architectural reasoning or investigation is required within a direction already selected or bounded by Sol; a large or risky refactor or migration is required; several subsystems must change together; regression risk is unusually high; existing behavior is contradictory or poorly understood; extensive investigation is necessary; multiple plausible solutions require careful comparison; debugging is state-dependent or intermittent; or correctness is particularly difficult to verify.
* Do not choose XHIGH merely because several files are involved, the work is mechanically large, many MCP calls are expected, the task may take a long time, the repository is large, or validation is repetitive. These indicate workload size, not necessarily reasoning difficulty.
* Start with HIGH unless the package clearly qualifies for XHIGH. Do not escalate after one trivial compiler error, one ordinary test failure, or another easily repairable issue. Let the same HIGH worker perform reasonable in-scope diagnosis and repair iterations first.
* Escalate from HIGH to XHIGH only on concrete evidence that deeper reasoning is useful: repeated unsuccessful diagnosis or repair, an unresolved root cause, contradictory evidence, newly discovered cross-system complexity, architectural ambiguity requiring deeper investigation, repeated failed validation, intermittent or state-dependent behavior, an inconclusive diagnosis, or HIGH explicitly reporting a genuine reasoning blocker. If investigation exposes a final architectural or cross-cutting decision, XHIGH returns evidence and options to Sol for decision before implementation continues under a revised bounded package.
* On escalation, preserve the package's ownership, scope, constraints, protected areas, acceptance criteria, and required validation. Give `luna_worker_xhigh` a compact evidence handoff covering what HIGH inspected or changed, actual failures and contradictory evidence, and remaining work. Do not make XHIGH rediscover the whole project unnecessarily. XHIGH becomes the production executor for the remaining package; Sol remains coordinator, reviewer, and final sign-off and does not take over implementation merely because HIGH could not finish.
